# 多模态文献问答 Agent：RAG-Anything 接入与基线评测计划

更新时间：2026-11-10  
状态：计划已制定；各阶段的实验结果需要实际运行后填写。

## 1. 我们这次要完成什么

在已有文献问答 Agent 的基础上，接入开源框架 RAG-Anything，并用同一批论文和问题比较：

1. **当前基线**：项目已有的 PDF 分页、BM25 与多语言向量混合检索、LangGraph 和 Qwen2.5-VL。
2. **RAG-Anything 方案**：使用 RAG-Anything 的文档解析与检索能力，并对接现有的本地模型、论文页码和 Agent。

最终应当得到：能复现的代码、明确标注来源和页码的评测集、两套方案的实际结果，以及对失败案例的解释。结果可能有提升，也可能没有；只记录实验中真实观察到的现象。

**本阶段不训练 LoRA/SFT。** 先弄清楚检索与图表问答的错误，再决定需要怎样的训练数据和微调目标。

## 2. 系统现在在哪里

```text
你的 Mac 浏览器
  上传论文 / 输入问题 / 查看回答和引用
       │
       │ SSH 隧道
       ▼
服务器上的项目目录：wjr3
  现有网页服务 → 检索 → Qwen2.5-VL → 答案与 PDF 物理页码
```

- 网页服务、模型和论文索引在 `wjr3` 中；浏览器只负责交互。
- 本计划和代码可以在电脑上查看；实际环境、实验数据与模型运行在服务器。
- 服务器上已有 `Qwen2.5-VL-3B-Instruct` 和多语言 MiniLM 模型，可优先复用。
- GitHub 仓库公开项目代码和说明。原始论文、模型权重、本地索引、缓存、日志及个人文件不应提交。

## 3. 开始之前的约定

1. 所有服务器工作放在 `wjr3`；不在 `wjr2` 中操作。
2. 不清空、覆盖已有 `data/web/`、用户上传的论文、现有索引或 `.conda` 环境。
3. RAG-Anything 使用项目内的独立实验目录和 Python 环境，避免直接替换当前网页依赖。实验目录计划放在已被 Git 忽略的 `data/raganything/` 下。
4. 查询空闲 GPU 后再安排重任务；控制并发和 CPU 线程，不终止其他人的进程。空闲状态只在检查时有效。
5. 不将本机端口或服务器服务暴露到公网，不在代码或日志中写入密钥。优先使用服务器已有的本地模型。
6. 先在实验路径验证，确认来源页码和原有功能正常后，再决定怎样把新方案呈现在网页里。

## 4. 第一步：检查现有环境和记录起点

### 要做的事

1. 查看 `wjr3` 的 Git 状态、Python 版本、现有依赖、模型路径和网页服务状态。
2. 记录服务器硬件、可用磁盘以及各 GPU 当前显存；记录是某一时刻的共享资源快照，不等于个人配额。
3. 核对当前代码的默认设置：PDF 如何切页和分块、是否建立向量、检索返回多少页、模型如何生成回答和引用。
4. 记录已有开发样例的位置，并区分开发样例与稍后新建的测试集。

### 验收标准

- 能确认实验位置、现有模型和服务进程。
- 能说明当前代码实际运行的检索配置。
- 记录环境信息，且不改变现有网页和论文库。

## 5. 第二步：建立基线评测集

### 为什么要先做评测

只有在同一批问题上比较两套方案，才能知道接入新框架后哪些地方变好、变差。现在仓库中的 3 道合成题和 6 道 RAG 原论文开发题主要用于检查流程，不能作为独立真实论文性能的依据。

### 计划怎样准备

1. 保留现有合成题和 RAG 原论文问题，作为**开发与调试集**。
2. 选择 2～3 篇可公开访问、与开发样例不同的论文，建立小规模**探索性测试集**。候选包括 Vision Transformer（arXiv:2010.11929）和 CLIP（arXiv:2103.00020）；以实际能够取得并核对的 PDF 为准。
3. 初步目标是约 15～30 道题，尽量覆盖正文事实、表格读取、图表趋势或比较，以及中英文提问。题目数量取决于人工核对是否完成，不为凑数量编造标签。
4. 每题保存：论文来源、PDF 文件标识、问题、参考答案、支持答案的 PDF **物理页码**、问题类型和核对依据。多个页面都足以支持答案时应如实记录。
5. 人工查看 PDF 原文、表格或图表，确认页码与参考答案。PDF 物理页码从 1 开始，可能不同于印刷页码。
6. 在运行对比前固定评测文件；实现调试主要使用开发集。若因为测试发现错误而调整系统，应记录调整，不能把反复调试过的结果描述为完全独立测试。

一个数据记录的示意如下，内容并不是已标注的真实题目：

```json
{
  "id": "paper-01-q01",
  "document": "paper-01.pdf",
  "question": "图中哪一组数值更高？",
  "answer": "需要按原文核对后填写",
  "pages": [3],
  "type": "figure",
  "evidence_note": "需要按原图和图注核对后填写"
}
```

### 验收标准

- 每道纳入统计的问题都能追溯到具体 PDF 页面。
- 文档来源、问题类型、答案和页码可检查。
- 清楚标注样本量、开发/测试用途与使用条件；论文 PDF 本身不提交仓库。
- 这个小集合用于探索和比较，不作为对所有论文的准确率保证。

## 6. 第三步：测量当前方案的基线

### 要做的事

1. 使用刚准备的论文建立**单独的实验索引**，不重建或覆盖网页正在使用的索引。
2. 记录基线选项：BM25、多语言 MiniLM、是否建立页面视觉描述、检索页数与模型版本。
3. 在同一评测集上运行检索。以当前网页使用的 `top_k=4` 作为主要比较口径，同时可报告第 1 页命中情况。部分问题只写了“图 1”，未写论文名，因此主要对照口径是先选中该题对应的论文，再检索该论文，模拟网页的单篇文献选择。
4. 对可以验证的答案运行真实模型问答，保存实际答案、引用、路由和耗时。
5. 统计和人工检查失败案例，尤其关注图表所在页未命中、模型读错图、表格值不一致、引用与答案不匹配。

### 主要记录哪些指标

- **页级 Hit@1 / Hit@4**：参考页是否出现在前 1 / 4 个不同候选页面中；报告分子、分母和缺失页数。
- **答案检查**：数值类优先精确核对；其他答案按参考证据进行人工判断。字符串匹配仅作辅助，不直接等于语义正确。
- **引用检查**：是否给出文档和页码，以及该页面是否真的支持答案；“有页码”不等于“证据正确”。
- **成本**：索引建立时间、问答耗时、显存与系统内存观察值；说明模型是否已预热、资源是否为共享快照。

### 验收标准

- 形成能逐题追溯的基线结果和运行命令。
- 原始结果同时包含成功与失败项，不只挑选演示成功的例子。
- 每个汇总数字附样本数；区分开发结果与探索性测试结果。

## 7. 第四步：建立 RAG-Anything 实验环境

### 要做的事

1. 核对 [RAG-Anything 官方项目](https://github.com/HKUDS/RAG-Anything)当前文档、依赖以及 PDF 解析器的版本兼容性。
2. 在 `data/raganything/` 下创建隔离的 Python 环境、缓存、索引和日志目录；保留当前 `.conda` 环境。
3. 根据服务器网络与 CUDA 情况安装并固定经过验证的依赖版本；记录安装命令和版本，不把临时机器路径写死为所有人的默认值。
4. 先使用小型合成 PDF 测试解析器能否运行，确认输出包含可定位的文本、图表或表格元素及页码信息。
5. 检查解析期间的内存、显存和磁盘增长。若依赖冲突、网络或资源不足，保留错误信息并寻找兼容方案；不把尚未成功运行的部分写成已完成。

### 验收标准

- 在隔离环境里可导入实际安装的 `raganything` 包，能运行一次最小解析。
- 不破坏原有网页或用户上传文件。
- 可复现环境版本与所需模型；记录解析耗时和资源占用。

## 8. 第五步：把 RAG-Anything 接到现有 Agent

### 预期流程

```text
PDF → RAG-Anything / 解析器 → 结构化内容与索引
用户问题 → RAG-Anything 检索 → 转换成现有 Agent 证据格式
         → LangGraph / Qwen2.5-VL → 回答 + 可核验的文档与页码
```

### 具体工作

1. 提供本地模型适配：把 RAG-Anything 需要的文本生成、图像理解和向量接口接到可用的本地模型；避免不必要的重复加载。
2. 建立独立索引和运行配置，记录使用的解析器、检索模式、模型版本与数据路径。
3. 将实际检索到的内容映射到现有 Agent 的“文档、物理页码、证据文本/图像”结构。
4. 仔细核对 RAG-Anything/底层检索结果是否保留可验证的页码。解析器的 `page_idx` 可能从 0 开始，显示时必须转换；跨页块和缺失页码需单独处理。
5. 对无法可靠映射到来源页码的证据标记为不可定位，统计比例；不能从回答文字中猜测页码或冒充精确引用。
6. 先通过命令行和自动化测试验证，再接入网页选择或以明确标识的实验入口展示。网页中只有经过核验的来源才提供点击预览。

### 验收标准

- 代码真正调用 RAG-Anything，而不只是安装依赖或修改名称。
- 同一篇 PDF 能完成解析、检索和回答；能核对的引用可以打开正确的原文页面。
- 对页码缺失、解析失败、模型加载失败和空结果有可理解的提示。
- 已有网页的 PDF 上传、现有问答路径和原始数据仍可使用。

## 9. 第六步：公平对比两套方案

1. 使用相同的 PDF 集合、固定的问题和参考页码；两套方案都先限定在问题对应的那一篇论文。
2. 尽可能复用相同 Qwen 模型与向量模型；不能保持一致的配置需要列出，不能把不同模型的影响全部归因于框架。
3. 尽可能统一到“前 4 个去重后的 PDF 页面”比较。若 RAG-Anything 返回的是文本块或图节点，需要注明转换方式；无法还原页码的结果计入不可定位并单独报告。
4. 分别统计文本题、图表题和表格题的页级命中、答案及引用检查，并公开各类样本数。
5. 比较建索引时间、单次问答耗时、显存占用、失败率和磁盘开销；测试期间说明是否有其他共享任务。
6. 保留逐题结果，说明代表性的成功与失败原因。没有足够证据时，不声称“准确率提升”。

## 10. 第七步：测试、文档与发布

1. 运行现有自动化测试，以及与新适配器相关的必要测试：页码转换、证据丢失、不同文档同页、错误处理等。
2. 用真实论文从头完成一次端到端检查：建索引、提问、查看答案、点击引用并对照 PDF。
3. 更新 README，说明新旧方案、安装方式、运行命令、实验数据来源、结果和限制。
4. 整理一份易读的中文实验报告，记录具体配置、资源与结果；原始输出保存在服务器忽略目录中。
5. 检查待公开内容，只把代码、说明、可公开的问题与实验结果同步到已有 GitHub 仓库。
6. 是否更新简历，依据实际完成的功能、真实结果和你亲自参与及理解的内容判断。
